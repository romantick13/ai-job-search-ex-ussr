# LOG-CONTRACT.md — контракт журналирования «никаких тихих игноров»

- Введён владельцем 2026-10-21. Обратная сила: весь код с WP-P0; новые файлы
  пишутся только по этому контракту.
- Формулировка владельца: «никаких тихих игноров — всё, абсолютно всё должно
  протоколироваться в лог на диске и параллельно выводиться в окне приложения
  в онлайне, все действия»; UI (дашборд с окошками) рисуется позже, но
  архитектура готова к нему с первого дня.

## 1. Машина протокола

Единственная точка — `ILogService` (`src/AiJobSearchBy/Services/ILogService.cs`,
реализация `LogService`). Каждое событие уходит в ДВА канала одновременно:

| Канал | Куда | Что |
|---|---|---|
| Диск | `%APPDATA%\ai-job-search-by\logs\ai-job-search-by-YYYYMMDD.log` | полный протокол, строка с миллисекундами, ротация по дате; `Clear()` его не трогает |
| Живая лента | `ObservableCollection<string> Logs` (кольцо 300) | CLI: дубль в stdout; WP-U: окна дашборда подписываются на ту же ленту |

Методы: `Log` (обычное действие), `LogSuccess` (успех шага), `LogError`
(ошибка/исключение), `LogWarn` (осознанный пропуск — обязательно с причиной),
`Clear` (очистить окно; диск продолжает писаться).

Формат строки окна: `[HH:mm:ss] текст`, для успеха/ошибки/пропуска — маркеры.
Формат строки диска: `[HH:mm:ss.fff] [HH:mm:ss] текст` — у окна точность до
секунды, у протокола до миллисекунды; двойное время сознательное.

Устойчивость: сбой записи на диск не роняет процесс и не молчит — сообщение в
stderr (первый сбой и далее каждый десятый) плюс счётчик `DiskWriteFailures`.
Если профильный каталог недоступен, протокол ведётся рядом с exe, и сам этот
фолбэк записывается первой строкой протокола.

## 2. Правила НИ (проверяются при код-ревью; превращаются в CI-гейты, когда появится анализатор)

- **НИ-1. Каждый catch обязан кричать.** В блоке `catch` — `LogError` или
  `LogWarn` с тремя вещами: что делали, что поймали, что решили. Ни одного
  catch без записи в протокол.
- **НИ-2. Тихих пропусков не существует.** `catch { }`, `catch { return null; }`
  и аналогичные молчаливые ветки запрещены. Осознанный пропуск оформляется как
  `LogWarn("skip: <что пропущено> — причина: <почему>")` и виден в окне.
- **НИ-3. Протокол сам не молчит и не роняет.** Сбой записи — см. §1.
- **НИ-4. Каждое действие пайплайна — событие.** Старт прогона, запрос к
  порталу, ответ, разбор страницы, находка вакансии, дедуп, запись, стоп,
  включение/выключение портала, обращение к AI — всё проходит через `Log*`.
  Если действия нет в окне — его не было.
- **НИ-5. Два канала обязательны всегда.** Никакой код не пишет «только в
  консоль» или «только в файл» в обход `ILogService`; `Console.WriteLine` в
  продуктовом коде запрещён (кроме самой машины протокола).

Это правило напрямую закрывает пункт релизного гейта «в логах есть понятная
причина по каждому упавшему порталу».

## 3. Карточка интеграции в существующий каркас

1. Регистрация (CompositionRoot, до остальных сервисов):
   `services.AddSingleton<ILogService, LogService>();`
2. Аварийные хендлеры в `Program.Main` — вешаются до любой содержательной
   работы, чтобы фатал тоже попал в протокол:

```csharp
var log = new LogService(); // %APPDATA%\ai-job-search-by\logs

AppDomain.CurrentDomain.UnhandledException += (_, e) =>
    log.LogError($"FATAL UnhandledException: {e.ExceptionObject}");

TaskScheduler.UnobservedTaskException += (_, e) =>
{
    log.LogError($"FATAL UnobservedTaskException: {e.Exception}");
    e.SetObserved(); // глушим падение процесса, но событие — в протокол
};
```

3. В тестах конструировать `new LogService(tmpDir, echoToConsole: false)`.
4. Прогнать аудит существующих файлов по чек-листу §4 и вшить протокол в
   найденные точки.

## 4. Чек-лист аудита «тишины» (по всему коду, при каждом WP)

- [ ] `grep -n "catch"` по всем .cs — у каждого catch есть Log* внутри
      (или re-throw, который логируется выше; само по себе `throw;` допустимо,
      если на пути вверх кто-то логирует).
- [ ] Ни одного `catch { }` / `catch { return ...; }` без Log*.
- [ ] Все развилки «сделать / пропустить» логируют решение (Log или LogWarn).
- [ ] Ни одного `Console.WriteLine` в продуктовом коде вне LogService.
- [ ] Ключевые события прогона стартуют/завершают запись (НИ-4): у адаптера —
      старт/страница/итог; у дедупа — найдено/скрыто; у записи БД — успех/сбой.
- [ ] В тестах: сценарий «сервис упал → в протоколе есть причина с контекстом».

## 5. Шаблоны кода

Ошибка с контекстом (НИ-1):

```csharp
try
{
    var html = await FetchPageAsync(page);
    log.LogSuccess($"портал {portalId}: страница {page} получена ({html.Length} символов)");
}
catch (HttpRequestException ex)
{
    // что делали / что поймали / что решили
    log.LogError($"портал {portalId}: GET страницы {page} упал — {ex.Message}; прерываю обход портала");
    throw; // решение — наверх, но причина уже в протоколе
}
```

Осознанный пропуск (НИ-2):

```csharp
if (string.IsNullOrWhiteSpace(externalId))
{
    log.LogWarn($"skip: вакансия без external_id от {portalId} — причина: разметка без якоря; пропускаю запись");
    continue;
}
```

## 6. Дашборд (WP-U)

Окна дашборда — подписчики ленты `Logs` (событие `CollectionChanged`), без
отдельного канала данных: окно журнала — вся лента; панели прогресса —
фильтр по событиям порталов; панель ошибок — фильтр по LogError/LogWarn со
счётчиками. Добавление панели = новый подписчик, машина протокола не меняется.
Пока UI нет, «окном приложения» служит stdout (EchoToConsole по умолчанию
включён; в будущей Avalonia-сборке отключается, чтобы не дублировать вывод).
