# MAINTENANCE.md — сопровождение и известные проблемы ai-job-search-by

Статус: канонический рабочий документ | Обновлён: 2026-10-20 | Владелец: ThreeI

Два тематических раздела: политика сопровождения соло-мейнтейнера и
публичный список известных проблем («Known issues»). Учреждён решением
владельца 2026-10-20 на основании DECISIONS.md (RFC-006 §2.6); вобрал
планировавшиеся ранее known-issues.md и portals-health.md. Смежные
документы: PLAN.md — план, статус и гейты релиза; DECISIONS.md — принятые
решения; troubleshooting.md — типовые проблемы пользователя;
config/registry.json — источник правды по порталам.

## 1. Политика сопровождения

### 1.1 Поддерживается только последний релиз

Поддерживается последний релиз — это должно быть правдой, а не лозунгом
(PLAN.md §8.3). Один релиз, который «пока работает», лучше, чем версия с
полным каталогом адаптеров в режиме пожизненной поддержки. Вопросы по
старым версиям закрываются с предложением обновиться до текущей.

### 1.2 Приоритеты починки

- Адаптеры, включённые в цепочку по умолчанию (ядро), чинятся в первую
  очередь: их поломка ломает первый запуск у новых пользователей.
- Experimental-адаптеры и источники с личным ключом = community-
  maintained: могут ждать до следующего релиза.
- Адаптер сломан больше 30 дней — помечается deprecated в README; в UI
  портал показывается как неработающий, а не молча возвращает 0 вакансий
  (PLAN.md §8.1, п. 6).

### 1.3 Ожидания по ответам — честные

Соло-мейнтейнер: ответа на issue может не быть неделями. Это заявлено
заранее, а не обещано «24 часа». Быстрее всего чинятся баг-репорты по
шаблону: точное сообщение об ошибке, журнал из
`%APPDATA%\ai-job-search-by\logs\`, дата и шаги воспроизведения.

### 1.4 Версии и журнал

Keep a Changelog + SemVer: фикс адаптера = patch; новый портал или фича
= minor. До первого релиза журнал живёт в PLAN.md §12.2, после первого
релиза выносится в CHANGELOG.md.

### 1.5 Maintenance mode

При паузе (low-energy) в README ставится бейдж «maintenance mode».
Проект не бросается — он замедляется; это нормальное состояние
соло-проекта, а не авария.

### 1.6 Чего точно не будет

- Обходов robots.txt, ToS и гео-блоков: ограничения описываются честно,
  без инструкций по VPN (PLAN.md §2, §8.1 п. 9).
- SLA и гарантированных сроков ответа на issues.
- Поддержки старых релизов и обратных портов исправлений.

и этого раздела одним коммитом (коммит фазы = код + доки вместе,
architecture.md §1).

Полные тексты проверенных документов в репозитории не хранятся: в доках
и реестре — дословные цитаты, ссылки и даты проверок; программные снимки
документов остаются в локальном архиве владельца (решение от 2026-10-20).

### 2.1 Ограничения v1 (это решения, а не баги)

- Автоматическая подача откликов не реализована намеренно: подача —
  только с подтверждением пользователя (PLAN.md §4).
- Квоты AI-провайдеров читаются в рантайме; числовые значения в
  документации не дублируются (PLAN.md §12.3).
- belmeta: официального пути доступа нет — ждать или исключать
  окончательно (PLAN.md §10).

## 3. Как сообщить о сломанном портале

1. Откройте issue по шаблону «портал сломался / изменились ToS».
2. Укажите: название портала, дату, что ожидалось и что вернулось
   (0 вакансий, 4xx/5xx, капча), по возможности — выдержку robots.txt
   или ToS с номером пункта.
3. Дальше работает гейт карточки (CONTRIBUTING.md, «Добавить портал»;
   DECISIONS.md, RFC-003 §2.11): новый статус фиксируется цитатой и
   датой в `tos_evidence` реестра; код без карточки не пишется.
