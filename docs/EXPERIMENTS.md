# Эксперименты: методология и результаты

Вместо журнала исправлений здесь живут измерения: что программа реально
сделала на живых данных, с какими ограничениями и что из этого следует.
Каждый прогон — с датой, средой и сырыми данными, чтобы цифры можно было
проверить. Обещания без измерений в README не делаются.

## Прогон 1: поиск hh-группы — 2026-10-28

**Вопрос:** сколько страница поиска реально отдаёт карточек, сколько из них
доходит до окна пользователя и где теряются.

**Метод:** три фиксированных запроса (`системный администратор`, `C#`,
`няня`) против живого `rabota.by`. Пайплайн — настоящий код приложения:
план страниц по счётчику и пагинатору, кэш страниц, разбор карточек
`HhByPortal`, дедуп (канонический URL → название+работодатель),
гео-фильтр с дефолтом «Беларусь + Россия», фильтр релевантности строки
запроса. Каждая скачанная страница сохранена как аудит-файл.

**Среда и её ограничения (честно):**

* Щит rabota.by отдал датацентровому IP этой тестовой среды глубокие
  страницы выдачи оболочкой без карточек (первая страница полная,
  страницы 2+ — как повезёт). Транспорт страниц в раннере — curl
  с заголовками браузера: TLS-отпечаток .NET HttpClient из этой среды
  щит отклонял сразу (HTTP 403).
* Из-за этого два запроса из трёх — **частичные**: собраны первые страницы
  (для «системный администратор» — 4 из 8, для «C#» — 1 из 3). Строки таблицы
  помечены честно как частичные.
* Между страницами раннер выдерживал паузу 2 с (вежливость эксперимента;
  в приложении паузы сняты — запросов там в разы меньше, чем страниц).

**Результаты:**

| Запрос | Счётчик сайта | Страниц по плану | Карточек собрано | Дублей отсечено (URL + название) | Скрыто фильтрами | Итог в окне |
|---|---|---|---|---|---|---|
| системный администратор *(частичный)* | 159 | 8 | 69 (стр. 1–4) | 3 + 1 | 0 гео, 19 нерелевантных | 46 |
| C# *(частичный)* | 45 | 3 | 20 (стр. 1) | 0 + 0 | 0 гео, 11 нерелевантных | 9 |
| няня *(полный)* | 12 | 1 | 11 | 0 + 0 | 0 гео, 7 нерелевантных | 4 |

Из собранного дошедшего: с зарплатой — 32/46, 1/9, 3/4; с распознанной
локацией — 46/46, 9/9, 4/4; с пометкой «можно удалённо» — 2, 6, 1.

**Наблюдения:**

1. **Дедуп перепостов работает на живых данных:** переписи одной вакансии
   под разными id («Специалист по ТО ПК (системный администратор)» — два
   раза подряд) и филиалы «Компания. Отдел» схлопываются по правилу
   «название + работодатель».
2. **Релевант-фильтр — главный «сборщик мусора»** в этих прогонах: по
   «няня» он спрятал 7 из 11 («Торговый представитель…», «Мерчендайзер…»
   — «ни одного слова запроса ни в заголовке, ни в тексте»); по ИТ-запросам
   — 19 и 11 из собранного. Причина шума — hh подмешивает к выдаче блок
   «похожих» со своего сайта; без фильтра он весь попал бы в окно.
3. **Гео-фильтр в этих прогонах не скрывал ничего** — и это хороший знак:
   чужие страны почти не доходят до него, их отсекает сам параметр региона
   `area` кода страны зеркала. Фильтр остаётся страховкой на «протёкшие» города.
4. **Время:** 28 с (8 стр., частичный), 14 с (3 стр.), 2,7 с (1 стр.) —
   вместе с паузами раннера и проверкой щита. Прогон в приложении
   быстрее: там страница одна — запрос.

**Сырые данные:** [experiments/2026-10-28-search.json](experiments/2026-10-28-search.json)
(протокол прогона — в локальном архиве владельца: журналы в репозитории
не публикуются).

**Чего этот прогон НЕ показывает** (и что измеряем дальше):

* качество и время адаптации резюме — нужен прогон с реальным резюме и
  живыми ключами провайдеров (шаблон ниже);
* полноту многостраничной выдачи вне щита тестовой среды;
* расход ИИ-квоты на реальный цикл «поиск → адаптация → письмо».

## Прогон 2: адаптация резюме — план

**Вопрос:** не выдумывает ли модель факты при адаптации и сколько стоит цикл.

**Метод (когда будет выполнен):** одно реальное резюме владельца, три
реальные вакансии (рус/рус/англ), фиксированные провайдеры; для каждого
отклика фиксируем: провайдер и модель, токены, время, число запросов, и —
главное — ручную сверку адаптированного текста с исходным резюме
по фактам (места, даты, навыки, цифры).

**Шаблон результата (заполняется по факту прогона):**

| Вакансия | Провайдер · модель | Запросов / токенов | Время | Фактических расхождений с исходником | Комментарий |
|---|---|---|---|---|---|
| — | — | — | — | — | — |

Пока прогона нет, единственное честное заявление такое: промпт адаптации
прямо запрещает модели добавлять опыт и навыки, которых нет в исходном
резюме, — но это инструкция модели, а не гарантия. Проверяйте черновик
перед отправкой (README, «Ограничения», п. 2).
